```python
from __future__ import annotations

import json
from pathlib import Path

from shelves.schema.chart_schema import ChartSpec, parse_chart
from shelves.translator.translate import translate_chart
from shelves.theme.merge import load_theme, merge_theme
from shelves.data.bind import resolve_data
from shelves.render.to_html import render_html


def compile_chart(
    yaml_text: str,
    *,
    theme_path: Path | None = None,
    no_theme: bool = False,
    models_dir: Path | str | None = None,
    rows: list[dict] | None = None,
) -> dict:
    """
    Run the chart compilation pipeline: parse → translate → theme → data.

    Returns a Vega-Lite spec dict (ready for render_html or JSON serialization).

    This is the single source of truth for chart compilation. All CLI tools,
    the studio server, and the dashboard composer call this function.

    Args:
        yaml_text: Raw YAML string for a chart spec.
        theme_path: Path to a custom theme YAML. None = use default theme.
        no_theme: If True, skip theme merging entirely.
        models_dir: Directory containing model YAML files.
        rows: Pre-fetched inline data rows. If None and no Cube source,
              data binding is skipped.

    Returns:
        Vega-Lite spec dict with theme and (optionally) data applied.

    Raises:
        pydantic.ValidationError: If the YAML is not a valid chart spec.
        yaml.YAMLError: If the YAML string is malformed.
        FileNotFoundError: If theme_path or models_dir doesn't exist.
    """
    # Step 1: Parse YAML → ChartSpec
    spec = parse_chart(yaml_text)

    # Step 2: Translate ChartSpec → Vega-Lite dict
    vl_spec = translate_chart(spec, models_dir=models_dir)

    # Step 3: Theme merge (unless no_theme)
    if not no_theme:
        theme = load_theme(theme_path)
        vl_spec = merge_theme(vl_spec, theme)

    # Step 4: Data binding (if rows provided)
    if rows is not None:
        vl_spec = resolve_data(vl_spec, spec, rows=rows)

    return vl_spec


def compile_chart_to_html(
    yaml_text: str,
    *,
    theme_path: Path | None = None,
    no_theme: bool = False,
    models_dir: Path | str | None = None,
    rows: list[dict] | None = None,
) -> str:
    """
    Full pipeline: YAML → Vega-Lite → HTML.

    Convenience wrapper around compile_chart + render_html.

    Returns a self-contained HTML string with embedded vegaEmbed.
    """
    # Step 1: Compile to Vega-Lite
    spec = parse_chart(yaml_text)
    vl_spec = translate_chart(spec, models_dir=models_dir)

    if not no_theme:
        theme = load_theme(theme_path)
        vl_spec = merge_theme(vl_spec, theme)

    if rows is not None:
        vl_spec = resolve_data(vl_spec, spec, rows=rows)

    # Step 2: Render to HTML
    return render_html(vl_spec, title=spec.sheet)
```

**Design note:** `compile_chart` deliberately does NOT handle the "auto-load from model source" logic (reading inline JSON from a model's `source.path`, or fetching from Cube when no rows are provided). That logic involves filesystem reads and HTTP calls that belong in the caller (CLI, dev server, studio). The pipeline function stays pure: if you pass `rows`, they get bound; if you don't, no data binding happens. This keeps the function testable without mocking filesystem or network.

The CLI callers that currently auto-resolve data will continue to do so — they'll call `compile_chart` without rows, then handle the data resolution themselves afterward. This matches the existing `resolve_data` API which already supports being called separately.

**Revised approach for callers that need auto-resolution:** To avoid still duplicating the "load model → check source type → resolve" logic in each caller, we add one more function:

```python
def compile_chart_with_data(
    yaml_text: str,
    *,
    theme_path: Path | None = None,
    no_theme: bool = False,
    models_dir: Path | str | None = None,
    rows: list[dict] | None = None,
    data_path: Path | None = None,
) -> tuple[dict, ChartSpec]:
    """
    Full pipeline including model-driven data resolution.

    Handles the three data modes:
    1. rows provided → bind directly
    2. data_path provided → load JSON from file, bind
    3. Neither → attempt model-based resolution (Cube or inline source path)

    Returns (vl_spec, chart_spec) tuple. The chart_spec is returned so callers
    can access spec.sheet for titles, filenames, etc.
    """
    spec = parse_chart(yaml_text)
    vl_spec = translate_chart(spec, models_dir=models_dir)

    if not no_theme:
        theme = load_theme(theme_path)
        vl_spec = merge_theme(vl_spec, theme)

    # Data resolution
    if rows is not None:
        vl_spec = resolve_data(vl_spec, spec, rows=rows)
    elif data_path is not None:
        file_rows = json.loads(data_path.read_text())
        vl_spec = resolve_data(vl_spec, spec, rows=file_rows)
    else:
        # Try model-based resolution
        try:
            from shelves.models.loader import load_model
            model = load_model(spec.data, models_dir=models_dir)
            if model.source and model.source.type == "inline":
                source_path = Path(model.source.path)
                if source_path.exists():
                    file_rows = json.loads(source_path.read_text())
                    vl_spec = resolve_data(vl_spec, spec, rows=file_rows)
            else:
                vl_spec = resolve_data(vl_spec, spec, models_dir=models_dir)
        except Exception:
            pass  # Data binding is best-effort when no explicit rows/path

    return vl_spec, spec
```

```python
def compile_chart(
    yaml_text: str,
    *,
    theme_path: Path | None = None,
    no_theme: bool = False,
    models_dir: Path | str | None = None,
) -> tuple[dict, ChartSpec]:

This is the cleanest design. The pipeline does the pure part (parse + translate + theme). Data binding remains the caller's responsibility because:
1. `cli/render.py` has `--no-data`, `--data <file>`, and model-auto-resolve modes
2. `cli/dev.py` has `--data <file>` and model-auto-resolve, plus sets width/height
3. `studio/server.py` always does model-auto-resolve with best-effort error handling
4. `compose/dashboard.py` does model-auto-resolve with inline source path resolution relative to `data_dir`

Each caller's data logic is slightly different — trying to unify it would mean a function with too many mode flags. The duplication in data resolution is 5-8 lines per caller, not 30+, and each variant genuinely differs.

def try_resolve_model_data(
    vl_spec: dict,
    spec: ChartSpec,
    *,
    models_dir: Path | str | None = None,
) -> dict:
    """
    Best-effort data resolution from model source.

    Loads the model, checks if it has an inline source path — if so, reads
    the JSON file and binds. If it has a Cube source, queries Cube.
    If anything fails, returns the spec unchanged.

from __future__ import annotations

import json
from pathlib import Path

from shelves.schema.chart_schema import ChartSpec, parse_chart
from shelves.translator.translate import translate_chart
from shelves.theme.merge import load_theme, merge_theme
from shelves.data.bind import resolve_data
from shelves.render.to_html import render_html


def compile_chart(
    yaml_text: str,
    *,
    theme_path: Path | None = None,
    no_theme: bool = False,
    models_dir: Path | str | None = None,
) -> tuple[dict, ChartSpec]:
    """
    Core chart pipeline: parse → translate → theme merge.

    Returns (vl_spec, chart_spec). The chart_spec is returned so callers
    can use spec.sheet for titles/filenames and spec.data for model loading.

    Does NOT bind data. Callers handle data resolution because each has
    different I/O requirements (--no-data flags, file paths, Cube queries).

    Args:
        yaml_text: Raw YAML string for a chart spec.
        theme_path: Path to a custom theme YAML. None = use default theme.
        no_theme: If True, skip theme merging entirely.
        models_dir: Directory containing model YAML files.

    Returns:
        Tuple of (vega_lite_spec_dict, parsed_chart_spec).

    Raises:
        pydantic.ValidationError: If the YAML is not a valid chart spec.
        yaml.YAMLError: If the YAML string is malformed.
        FileNotFoundError: If theme_path doesn't exist.
    """
    # Step 1: Parse
    spec = parse_chart(yaml_text)

    # Step 2: Translate
    vl_spec = translate_chart(spec, models_dir=models_dir)

    # Step 3: Theme
    if not no_theme:
        theme = load_theme(theme_path)
        vl_spec = merge_theme(vl_spec, theme)

    return vl_spec, spec


def try_resolve_model_data(
    vl_spec: dict,
    spec: ChartSpec,
    *,
    models_dir: Path | str | None = None,
) -> dict:
    """
    Best-effort data resolution from the chart's model source.

    Loads the model for spec.data, checks the source type:
    - inline: reads JSON from the source path and binds
    - cube: queries Cube.dev API and binds
    - no source / failure: returns vl_spec unchanged

    This consolidates the "auto-resolve from model" pattern that was
    duplicated across cli/render.py, cli/dev.py, and studio/server.py.

    Args:
        vl_spec: Compiled Vega-Lite spec (no data yet).
        spec: Parsed ChartSpec (needed for field extraction).
        models_dir: Optional models directory path.

    Returns:
        Vega-Lite spec, possibly with data attached.
    """
    # Step 1: Load model
    from shelves.models.loader import load_model
    model = load_model(spec.data, models_dir=models_dir)

    # Step 2: Route by source type
    if model.source and model.source.type == "inline":
        source_path = Path(model.source.path)
        if source_path.exists():
            rows = json.loads(source_path.read_text())
            return resolve_data(vl_spec, spec, rows=rows)
        return vl_spec
    else:
        return resolve_data(vl_spec, spec, models_dir=models_dir)

async def _compile_yaml(request: Request) -> JSONResponse:
    """POST /compile — compile YAML body to Vega-Lite spec."""
    import yaml as _yaml
    from shelves.pipeline import compile_chart, resolve_model_data

    yaml_body = (await request.body()).decode("utf-8")

    if not yaml_body.strip():
        return JSONResponse({"vega_lite_spec": None, "errors": ["Empty YAML body"], "warnings": []})

    try:
        raw = _yaml.safe_load(yaml_body)
        if not isinstance(raw, dict) or "sheet" not in raw:
            return JSONResponse({"vega_lite_spec": None, "errors": [], "warnings": []})
    except Exception:
        pass

    try:
        vl_spec, spec = compile_chart(
            yaml_body,
            theme_path=request.app.state.theme_path,
            models_dir=request.app.state.models_dir if request.app.state.models_dir.exists() else None,
        )
    except Exception as e:
        return JSONResponse({"vega_lite_spec": None, "errors": [str(e)], "warnings": []})

    warnings: list[str] = []
    try:
        vl_spec = resolve_model_data(vl_spec, spec, models_dir=request.app.state.models_dir)
    except Exception as e:
        warnings.append(f"Data resolution skipped: {e}")

    return JSONResponse({"vega_lite_spec": vl_spec, "errors": [], "warnings": warnings})
```

Note: the current code has separate try/except blocks for parse, translate, and theme. The new version collapses them into one `compile_chart` call. If parse fails, the error is still returned to the client — just not distinguishable from a translate error. This is acceptable since both are "compilation errors" from the user's perspective.

```python
def resolve_model_data(
    vl_spec: dict,
    spec: ChartSpec,
    *,
    models_dir: Path | str | None = None,
    data_base_dir: Path | None = None,
) -> dict:
    """
    Resolve data from the chart's model source.

    Args:
        models_dir: Models directory for loading model definitions.
        data_base_dir: Base directory for resolving relative inline source
                      paths. If None, paths are resolved as-is.
    """
    from shelves.models.loader import load_model
    model = load_model(spec.data, models_dir=models_dir)

    if model.source and model.source.type == "inline":
        source_path = Path(model.source.path)
        if data_base_dir and not source_path.is_absolute():
            source_path = data_base_dir / source_path
        if source_path.exists():
            rows = json.loads(source_path.read_text())
            return resolve_data(vl_spec, spec, rows=rows)
        return vl_spec
    else:
        return resolve_data(vl_spec, spec, models_dir=models_dir)
```

## Addendum — Studio server data resolution consolidation

**Date:** 2026-05-22

### Background

During initial implementation, the studio server's data resolution in `_compile_yaml` and `_compile_file_and_broadcast` was left calling `resolve_data` directly (rather than `resolve_model_data` like the other 3 callers). This was a hack to preserve two existing tests:

- `test_compile_calls_resolve_data` — mocked `shelves.data.bind.resolve_data` against an inline-source `orders` model
- `test_compile_data_resolution_failure_returns_warning` — same setup

Keeping `resolve_data` direct in the server defeated the purpose of the refactor — the server retained its own slightly-different data-resolution pattern, re-creating the duplication the ticket aimed to eliminate.

### What was changed

1. **`shelves/studio/server.py`** — `_compile_yaml` and `_compile_file_and_broadcast` now call `resolve_model_data(vl_spec, spec, models_dir=models_dir)` instead of `resolve_data(vl_spec, spec, models_dir=models_dir)`. The server is now fully aligned with the other callers (`cli/render.py`, `cli/dev.py`, `compose/dashboard.py`).

2. **`tests/test_studio_cli.py`** — three updates in `TestCompileEndpoint`:
   - Added a `_CUBE_YAML` class constant pointing to the existing `cube_orders` Cube-source model fixture.
   - `test_compile_calls_resolve_data` and `test_compile_data_resolution_failure_returns_warning` now POST `_CUBE_YAML` (not `_VALID_YAML`). The mock on `shelves.data.bind.resolve_data` is still triggered because `resolve_model_data` calls `resolve_data` on the cube branch.
   - Added `test_compile_inline_model_missing_path_no_warning` to capture the desired improved behavior: with an inline model whose relative `source.path` doesn't exist relative to the test CWD, the server now returns the spec with NO warning (previously it warned about Cube being missing, because the old `resolve_data` direct call always tried Cube for any source type).

### Behavioral improvement

For inline models, the studio server now matches the behavior of the CLI render and dev-server callers:

| Source type | File exists? | Old behavior (direct `resolve_data`) | New behavior (`resolve_model_data`) |
|-------------|--------------|--------------------------------------|--------------------------------------|
| inline      | yes          | Raises `ValueError` → warning        | Reads file, binds data — no warning  |
| inline      | no           | Raises `ValueError` → warning        | Silent skip — no warning             |
| cube        | n/a          | Queries Cube (or warning on failure) | Queries Cube (or warning on failure) — unchanged |

For studio users, this means: opening a chart that uses an inline model with data already on disk now renders the data correctly (previously the server only worked for Cube models — inline models would always show "Data resolution skipped").
